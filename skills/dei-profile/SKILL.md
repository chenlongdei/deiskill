# dei-profile 个人介绍与案例库

## 使命

让一个人出门**说得清自己是谁、凭什么信他、怎么开始合作**，并且每次讲课、见人、发资料时，都能从自己的案例库里挑出最对路的那几个，而不是每次从头想。

介绍和案例是同一个库的两种用法：**案例库是原料，介绍、话术、PPT 页、PDF 是成品。**

## 铁律

1. **不编**：数字、客户原话、截图、媒体报道只用用户给的。用户给的数字直接用；推算出来的数字必须写出依据，放进「估算口径」附录，正文里能被追问、能答得上来。缺的地方留 `` `[待补：××]` ``。
2. **分清谁做的**：每个案例标明是「亲手交付」「学员自己做的」「授课 / 讲座」还是「个人成绩」。亲手做的证明能交付，学员做的证明方法能复制，两者不能混写。拿不准就问用户，不猜。
3. **先结果后过程**：标题写结果（「老板每天少算 2 小时账」），不写「案例一」；正文不报工具名，报工具名只在面向技术人群时用。
4. **大白话**：初中学历的老板也能听懂。不用「高频词温差」「赋能闭环」这类词，不用「割韭菜」「抓内鬼」这类刺激性的词，不拉踩同行。
5. **观点要有「正确的非共识」**：介绍里要有几句和对方平时听到的不一样、但站得住的判断。对读者过去走的弯路：能解决就给方法，解决不了就说明问题不在他。
6. **按读者分版本**：老板关心省多少、赚多少；个人关心能不能学会、能不能变现；机关、国企、社区关心安全合规、有没有成果亮点、能不能写进总结。同一个案例，对不同读者讲法不同。
7. **内部的东西不外发**：估算口径、谈判空间、话术、待确认清单写在文档末尾「# 附录（内部用，对外删除）」之后；PDF 和文档平台同步都不含这一部分。
8. **按用户的说话习惯写话术**：先读库里的话术文件和用户原话（录音、对话记录），用他的口头禅和句式；用户说「这句我平时不会这么说」就按他的原话改。

## 流程

### Step 0 找到介绍库

1. 运行 `python3 scripts/profile_lib.py where`（Windows 上通常换成 `python`）。它按顺序找：本 Skill 的 `config.json` 里的 `library_root` → dei 工作区的 `05_成品/个人介绍/`。
2. 报「还没有介绍库」时：问用户已有的介绍材料放在哪（给 2—3 个建议，默认建议工作区 `05_成品/个人介绍/`），确认后 `python3 scripts/profile_lib.py init <路径>` 建骨架；用户已有自己的文件夹，就 `init` 到那个文件夹并记进 `config.json`，不搬动用户的文件。
3. 报「找不到」时说明哪个路径失效（外接盘没挂载、云盘未同步），请用户决定，不新建。
4. 库里有 `CLAUDE.md` 或 `profile.json` 时先读：里面有这个人的品牌名、城市、价格、写错过的事实和偏好，优先级高于本 Skill 的默认写法。

### Step 1 判断要做哪件事

| 用户说的 | 做什么 | 读什么 |
| --- | --- | --- |
| 「帮我梳理个人介绍」「我出门说不清自己」，并给了一堆素材 | 建库：诊断 → 去伪存真 → 分三层证据 → 写主介绍 → 拆案例卡片 | `references/library.md`、`references/writing-rules.md` |
| 「这是个新案例」，或发来录音、截图、数字 | 入库：归类 → 算账 → 卡片 → 更新介绍 | `references/case-intake.md` |
| 「这是我的背景资料」，或发来讲自己经历的分享稿、访谈 | 存原件 → 提炼进人物档案 → 新案例建卡 → 列出和已有材料的冲突 | `references/library.md` 第四节 |
| 「按这个主题 / 这份课程手册配案例」「明天去 XX 讲课」 | 筛案例 → 定制介绍和案例页 | `references/tailor.md` |
| 「见 XX 怎么介绍自己」「给我 1 / 3 / 10 分钟版」「朋友介绍我怎么说」「陌拜怎么开口」 | 定制话术 | `references/tailor.md` 第三节 |
| 「讲课用的 PPT 介绍页」 | 人物页 + 案例页文案 | `references/tailor.md` 第四节 |
| 「给政企 / 老板 / 个人出一版」「从客户角度再优化」 | 新版本或改版 | `references/writing-rules.md` |
| 「出 PDF」「发 XX 看的那份」「同步到 Notion / 飞书」 | 成品与同步 | `references/publish.md` |

### Step 2 筛案例（定制类任务都先做这一步）

```bash
python3 scripts/profile_lib.py cases --query "餐饮 获客 门店" --audience 老板 --top 5
```

它按关键词、读者、问题类型给案例卡片打分，返回 JSON 清单。**分数只是初筛**：读进前几张卡片，按 `references/tailor.md` 的规则挑 1—3 个，每个写一句「为什么选它」。案例卡片有改动后运行 `python3 scripts/profile_lib.py index` 重建 `案例索引.md`。

### Step 3 写成品，再自查

按对应 reference 写。交付前用 `references/writing-rules.md` 末尾的「客户视角检查清单」过一遍，并确认铁律 1、2、7。

### Step 4 记录

改了库里的文件后：

- 案例卡片有增删改 → `profile_lib.py index`；
- 对外文档有改动 → 按 `references/publish.md` 重新生成 PDF，问一句要不要同步到文档平台；
- 库是 Git 仓库时，提醒用户提交（用户明确要求才替他提交和推送）；
- `python3 scripts/dei_workspace.py log dei-profile <任务> ok <产出路径>` 记进运行总账。

## 缺少信息时

- 不知道读者是谁：先按最可能的读者给一版，并说明换成别的读者时哪几处要改。
- 案例缺数字：写成「原来 → 现在」的工序对比（一天 1 条 → 一天 9 条），不硬造金额；能按行业常识推算的，推算并写进估算口径，告诉用户哪几个数是推的。
- 不知道能不能点名客户或学员：先用「全国连锁摄影品牌」这类描述，问用户后再改成真名。

## 边界与停止条件

- 介绍库路径失效、文档平台未登录：停下说明缺什么、怎么补。
- 生成 PDF 需要 Python 的 `markdown` 包和 Google Chrome（或 Chromium / Edge）；缺哪个就给一条安装命令，用户同意后再装。
- 不替用户对外发送、不开公开分享。

## 输出

- 介绍库内：`01_个人介绍/`（各版本介绍、话术、PPT 文案）、`02_PDF/`、`03_参考资料/`、`05_案例库/`（一案一卡 + `案例索引.md`）。
- 筛案例、定制话术这类一次性任务：直接在对话里给出；用户要留存时，写进 `01_个人介绍/定制/YYYY-MM-DD_主题.md`。
- 给 PDF 时写出完整路径。

## 禁止事项

- 不编数字、不编客户原话和截图，不把学员做的写成自己交付的。
- 不把内部附录放进 PDF 或文档平台。
- 不在 Skill 目录里存用户的介绍和案例。

完成当前任务后直接结束。用户的请求超出本 Skill 范围，或询问下一步时，用一句话说明还需要哪种能力，不点名其他 Skill；当前环境已经安装 `dei` 时，补一句「可以用 `$dei` 继续」。
